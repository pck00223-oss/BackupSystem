# BackupSystem 答辩问答框架

> 用法：老师不会问具体代码实现，重点在**分层框架、类的构建、接口设计、各模块用的算法/库**。
> 本文件按"问—答"组织，答案可直接背诵。标注【背】的是必答要点，标注【懂】的是需要理解、能展开的设计原理。

---

## 一、项目整体架构（框架类问题，开场必问）

### Q1：先简单介绍一下你的项目。
【背】这是一个 Windows 平台的**本地数据备份与恢复系统**，用 C++17 编写。核心能力包括：全量/增量备份、文件元数据保留、自定义筛选备份、TAR 打包解包、**Huffman 和 RLE 两种手写压缩**、AES-256 和 3DES 两种加密、快照与时间点恢复、完整性校验、定时备份，以及一个纯 Win32 图形界面。所有功能都有单元测试覆盖。

### Q2：你的整体架构是怎么分层的？
【背】采用**分层架构 + 单一职责**，从上到下五层，依赖只能向下依赖：

| 层 | 目录 | 职责 | 主要类 |
|---|---|---|---|
| GUI 层 | gui/ | 图形界面、用户交互 | MainWindow、TaskStore |
| 应用层 | app/ | 任务封装、配置加载、调度 | BackupTask、ConfigLoader、TaskScheduler、ScheduleManager |
| 业务层 | business/ | 备份/恢复/校验/比较的流程组织 | BackupManager、RestoreManager、VerifyManager、FileComparator、FileFilter、Manifest、SnapshotManager |
| 引擎层 | engine/ | 文件扫描、复制、打包、OS 封装 | FileScanner、FileCopier、FileSystem、TarPacker |
| 核心层 | core/ | 数据结构、压缩、加密、哈希、日志、工具 | ICompressionAlgorithm、HuffmanCompressor、RleCompressor、CompressedFile、IEncryptionAlgorithm、AesCipher、TripleDesCipher、HashCalculator、BackupConfig、Logger |

【懂】分层的好处：上层只依赖下层的接口，换底层实现（比如换加密库）不影响上层；每个类职责单一，避免一个巨型类什么都干。

### Q3：项目是怎么构建的？怎么"变成库"？
【背】用 **CMake + Ninja** 构建，编译器是 MinGW-w64 的 g++。核心业务代码先编译成一个**静态库 `backup_core`**，然后两个可执行文件链接它：
- `backupapp`：命令行入口（main.cpp）
- `backupgui`：图形界面入口（WIN32，纯 Win32 API）
- `backup_tests`：测试程序

【懂】这就是"库化"思想：业务逻辑沉淀在 `backup_core` 静态库里，命令行、GUI、测试都是它的不同"前端"，同一份逻辑不重复实现。第三方库 GoogleTest 优先找系统安装，找不到时用 CMake 的 FetchContent 自动拉取固定版本 v1.15.2。

### Q4：你用到了哪些设计模式？
【背】四个主要的：

| 模式 | 用在哪 | 解决什么问题 |
|---|---|---|
| 策略模式 | IEncryptionAlgorithm + AesCipher/TripleDesCipher；ICompressionAlgorithm + HuffmanCompressor/RleCompressor | 算法可互换，管理器只依赖接口 |
| 工厂模式 | createEncryptionAlgorithm()、createCompressionAlgorithm() | 按名字创建算法实例，隐藏具体类 |
| RAII | FileHandle、BackupLockGuard | 句柄/锁在析构时自动释放，防止泄漏 |
| 单例模式 | Logger::instance() | 全系统一个日志器，统一出口 |

## 二、类的构建与接口实现（高频）

### Q5：重点讲一下你的加密接口是怎么设计的。
【背】定义了一个抽象基类（接口）`IEncryptionAlgorithm`，用纯虚函数规定了加密器必须实现的能力：
- `name()`：算法标识，写入 Manifest（"aes256"/"3des"）
- `blockSize()`、`keySize()`：块大小和密钥长度
- `encrypt()` / `decrypt()`：一次性加解密
- `generateRandomIv()`：生成随机初始向量 IV
- `encryptCbcBlocks()` / `decryptCbcBlocks()`：CBC 流式分块处理，给大文件用

然后有一个中间基类 `BcryptBlockCipher` 实现这些接口的**通用 CBC 逻辑**，具体的 `AesCipher` 和 `TripleDesCipher` 只提供算法参数（算法 ID、块大小、密钥长度），不重复写流程。

### Q6：为什么要搞一个抽象接口，直接写两个加密类不行吗？
【懂】这是**开闭原则 + 依赖倒置**：
- BackupManager/RestoreManager 只依赖 `IEncryptionAlgorithm` 接口，不依赖具体算法。
- 以后要加第三种算法（比如 SM4），只要新增一个子类、在工厂里注册，**管理器代码一行都不用改**。
- 测试时也方便用接口替换、做 NIST 标准向量验证。

### Q7：工厂函数具体怎么工作的？
【背】`createEncryptionAlgorithm(name, password)`：传入算法名和密码，内部判断——"aes256" 就返回 AesCipher 对象，"3des" 就返回 TripleDesCipher 对象，未知名字返回 nullptr。调用方拿到的是 `unique_ptr<IEncryptionAlgorithm>` 接口指针，不接触具体类。

### Q8：介绍一下你认为最核心的几个类各自管什么。
【背】

| 类 | 单一职责 |
|---|---|
| BackupManager | 组织一次备份的完整流程：扫描→筛选→比较→复制→存 Manifest→记历史，自己不做底层读写 |
| RestoreManager | 读 Manifest、建目录、恢复文件和元数据、做 Hash 校验 |
| FileScanner | 先序遍历递归扫描目录树，为每个条目生成 FileInfo |
| FileSystem | 集中封装 Win32 文件 API，业务层不直接调 Win32 |
| Manifest | 备份清单（key=value 文本），是增量、恢复、校验的共同数据基础 |
| SnapshotManager | 快照创建/列表/清理/时间点恢复，未变化文件用硬链接省空间 |
| VerifyManager | 按 Manifest 校验 data/ 里文件是否存在、Hash 是否一致，支持 --repair |
| FileComparator | 两级变更检测，识别新增/修改/删除/未变化 |

### Q9：FileInfo 这个结构为什么到处都在用？
【懂】FileInfo 对应 Unix 的 **inode 文件头**，是扫描、比较、清单、筛选、打包共用的数据载体，记录一个文件的全部元数据：类型、权限 mode、大小、创建/修改时间、卷序列号+文件索引（对应 inode 号）、硬链接计数、硬链接/软链接目标、内容 Hash。统一它就避免了各模块各定义一套文件结构、来回转换。

## 三、各模块用的算法 / 库（最高频，逐个模块）

### 【加密解密】

### Q10：你用了哪两种加密算法？
【背】两种对称分组密码，都工作在 **CBC 模式**：

| 算法 | 块大小 | 密钥长度 | 算法标识 |
|---|---|---|---|
| AES-256-CBC | 16 字节 | 32 字节（256 位） | aes256 |
| 3DES-CBC | 8 字节 | 24 字节（192 位） | 3des |

### Q11：加密是自己写的算法吗？调用的什么库？
【背】**完全不手写**，调用 Windows 系统自带的 **CNG（Cryptography Next Generation）库，即 bcrypt.dll**，核心函数是 `BCryptEncrypt` / `BCryptDecrypt`，算法通过 `BCRYPT_AES_ALGORITHM` 和 `BCRYPT_3DES_ALGORITHM` 打开。不写任何轮函数、S-box。
【懂】调库优先的原因：系统库经过安全验证、能抵抗常见攻击、维护成本低；自己手写分组密码极易引入安全漏洞。

### Q12：用户密码怎么变成加密密钥的？
【背】对用户密码做一次 **SHA-256** 得到 32 字节摘要，再按算法需要的 keySize 截取（AES 用满 32 字节，3DES 取前 24 字节）。

### Q13：IV（初始向量）是什么、怎么生成的？为什么需要它？
【背】IV 用 **BCryptGenRandom** 生成密码学安全随机数，每次加密都不同。加密输出格式是"**IV + 密文**"，解密时先读出 IV。
【懂】CBC 模式下随机 IV 保证即使相同明文、相同密钥，每次密文也不同，防止通过相同密文推断内容。

### Q14：数据长度不是块的整数倍怎么办？
【背】用 **PKCS7 填充**补齐到块的整数倍（由 BCrypt 处理），空文件也会产生一个完整填充块；解密后去掉填充。

### Q15：解密时怎么快速判断密码输错了？（老师明确要求的"加快校验"）
【背】备份时会计算一个**密码验证标记** `passwordVerifier = SHA256(密码 + 固定盐)` 写进 Manifest。恢复时用户输入密码，先重算这个标记和 Manifest 里的比对：
- **不一致 → 立刻判定密码错误，直接返回，不去解密整个文件**，避免对全部数据做一遍昂贵解密后才发现密码错。
- 一致才进入实际解密。
【懂】这不是密码的安全存储，只是一个快速前置校验；固定盐保持不变以兼容历史 Manifest。

### Q16：大文件加密怎么避免一次性占满内存？
【背】用接口里的 `encryptCbcBlocks/decryptCbcBlocks` 做**分块流式处理**，每次只处理若干完整块，CBC 的链式状态（前一密文块）在块之间传递，最后一块的填充由调用方统一处理。

### 【压缩解压】

### Q16A：你用了哪两种压缩算法？手写还是调库？
【背】两种：**Huffman（哈夫曼编码）和 RLE（行程编码），都是自己手写实现**，零第三方压缩库，只用 C++ 标准库。和加密"调库优先"不同，课程 PPT 用整整一讲要求理解 Huffman 原理，所以这里手写。两者都实现统一接口 `ICompressionAlgorithm`（`name/compress/decompress`），工厂按 "huffman"/"rle" 创建，管理器只面向接口。

### Q16B：讲一下 Huffman 编码的原理和流程。
【背】核心思想：**频率高的字节用短编码、频率低的用长编码**，让整体加权平均长度最短。流程：
1. 统计 256 种字节各自的词频；
2. 每个符号作为叶子节点放进**最小堆**；
3. 反复取权值最小的两个节点合并成新节点（权值为两者之和）放回堆，直到只剩一个根节点；
4. 从根到叶子，左走标 0、右走标 1，得到每个字节的**前缀码**；
5. 按码把数据写成比特流。
【懂】前缀码保证任何一个码都不是另一个码的前缀，解码时不会产生歧义。

### Q16C：什么是 WPL？为什么用最小堆？
【懂】WPL（带权路径长度）= 所有叶子的"权值 × 到根路径长度"之和，也就是编码后的总比特数；Huffman 树让 WPL 最小。最小堆每次 O(log n) 取出当前最小的两个节点，是贪心策略的高效实现，整体 O(n log n)。

### Q16D：按位编码时，字节末尾补位怎么处理？
【背】比特流不一定是 8 的整数倍，最后一个字节用 0 补齐，同时在数据里记录**有效比特数 validBits**；解码时只读有效位、忽略补位，不会解出多余符号。

### Q16E：解压时怎么还原？编码表怎么存？
【背】采用"**存词频表**"方式：压缩数据依次写原始长度、符号数、每个符号及其词频，再写比特流。解压时读出词频，用和压缩完全相同的最小堆算法**重建同一棵 Huffman 树**，再沿比特流从根走到叶子逐个还原字节。不必存完整树，也不用存编码字符串。单符号特例编码为 "0"，按原始长度还原。

### Q16F：RLE 是什么？packet 设计为什么能抗膨胀？
【背】RLE（行程编码）把连续重复的字节用"值 + 重复次数"表示。我用带类型的 packet，每个包 1 字节头 + 数据：
- bit7=1 重复包：低 7 位+1 为次数（1..128），后跟 1 字节；
- bit7=0 字面量包：低 7 位+1 为字节数，后跟对应字面量。
【懂】遇到重复走重复包、随机数据走字面量包，所以即使数据完全随机也只有约 1/128 的固定头部开销，避免朴素 RLE 把单个字节膨胀成"值+次数"。

### Q16G：大文件怎么压缩？压缩和加密怎么配合？
【背】文件按 **1MB 分块**，每块独立压缩，写入自描述容器（魔数 "BKCP" + 块数 + 每块[原始大小/压缩大小/数据]），内存只占一个块，临时文件 + 原子替换。压缩与加密组合时**先压缩再加密**（明文有冗余才压得动，加密后高熵压不动），恢复时**先解密再解压**，顺序严格相反。增量备份按算法名做一致性检查，换压缩算法（含 huffman↔rle）会被拒绝、要求全量重建，避免混血仓库。

### 【哈希与完整性】

### Q17：Hash 用的什么算法？用在哪？
【背】**SHA-256**，输出 64 位小写十六进制。三个用途：
1. 增量备份的**两级变更检测**（见 Q18）；
2. 恢复后校验文件内容；
3. VerifyManager 做完整性校验。
文件 Hash 分块读取计算，避免大文件占内存。

### Q18：增量备份怎么判断一个文件变没变？（两级变更检测）
【背】FileComparator 把当前扫描结果和上一次 Manifest 比：
- 路径历史里没有 → **新增 Added**
- 大小变了 → **修改 Modified**
- 大小和修改时间都相同 → **未变化 Unchanged**
- 大小相同但修改时间变了 → **算 SHA-256 二次确认**，Hash 不同才算修改
【懂】先用"大小+时间"做廉价判断，只有可疑时才算 Hash（贵），兼顾效率和准确；Hash 算不了时保守地当作修改，不会漏备份。

### 【打包解包】

### Q19：TAR 打包是用的第三方库吗？
【背】**自己实现的 ustar 格式 TAR**（POSIX IEEE P1003.1 标准），零第三方依赖，只用标准库和已有的 FileSystem 封装。
【懂】结构是 512 字节为一个块：每个条目一个 512 字节头（Header）+ 文件数据 + 补齐到 512 倍数的填充（Padding），最后两个全零块表示结束。

### Q20：TAR 里怎么区分和处理硬链接、软链接？
【背】用头部的 **typeflag（类型标志）**：

| typeflag | 类型 | 处理 |
|---|---|---|
| '0' | 普通文件 | 写/读文件内容 |
| '5' | 目录 | 建目录 |
| '1' | 硬链接 HARDLINK | 解包时 CreateHardLinkW，linkname 指向首个归档路径 |
| '2' | 符号链接 SYMLINK | 解包时 CreateSymbolicLinkW，linkname 记录目标，不跟随内容 |

【懂】硬链接：同一文件 ID（卷+inode）的多个硬链接，第一个按普通文件存，后面的存为 HARDLINK 指向第一个，避免重复存数据。打包用**先序遍历**扫描目录树。

### 【文件系统 / 元数据】

### Q21：文件操作为什么要再包一层 FileSystem？
【背】把所有 Win32 API（CreateFileW、ReadFile、WriteFile、FindFirstFileW、CreateHardLinkW 等）集中封装在 FileSystem 里，业务层不直接调系统 API，统一了错误处理，也方便测试。句柄用 FileHandle 做 RAII，出作用域自动 CloseHandle。

### Q22：元数据（权限、时间）怎么保留和恢复？
【背】扫描时把权限位（mode，Windows 简化映射为目录 0755/文件 0644）、创建/修改时间记录进 FileInfo 和 Manifest，恢复时用 `setFileTimes` 还原时间。还记录了 100ns 精度的 FILETIME，用于同秒内内容变化的精确检测。

### Q23：硬链接和符号链接有什么区别？
【懂】
- **硬链接**：多个目录项指向同一个 inode/物理文件，共享数据，必须在同一卷，删一个不影响其他，链接计数 +1。用 CreateHardLinkW。
- **符号链接**：一个特殊文件，存的是目标路径（可跨卷、可指向目录），删目标后链接失效。用 CreateSymbolicLinkW，**需要开发者模式或管理员权限**。

### 【图形界面】

### Q24：你的 GUI 是用 Qt 实现的吗？
【背】**不是 Qt，是纯 Win32 原生 API** 写的（CreateWindowExW、对话框、控件、消息循环），零第三方 GUI 依赖。MainWindow 管主窗口和任务列表，后台备份放在独立 worker 线程，通过自定义 Windows 消息（WM_USER+N）把日志和结果安全地传回 UI 线程。
【懂】选 Win32 是为了零依赖、体积小、体现对操作系统 API 的掌握；代价是代码比 Qt 啰嗦。

### 【定时备份】

### Q25：定时备份怎么实现的？
【背】提供了两种方式：
1. **TaskScheduler**：进程内后台线程，每 30 秒检查一次，命中配置的 HH:MM 且当天没执行过就触发，支持立即执行 runNow。
2. **ScheduleManager**：把任务注册进 **Windows 任务计划程序**，到点系统启动 backupapp 执行一次后退出，程序不用常驻，适合长期自用。

### 【配置 / 日志 / 锁 / 本地密码】

### Q26：配置文件用什么格式？
【背】简单的自定义 **key=value** 文本格式（ConfigLoader 解析），故意不引第三方配置库以减少依赖；非法字段写入警告而不是中断解析。

### Q27：日志怎么设计的？
【背】自研 Logger 单例，分 Info/Warning/Error 三级，同时输出控制台和文件，线程安全（加锁）。**密码等敏感信息绝不写进普通日志**。

### Q28：怎么防止两个备份同时写一个目录？
【背】BackupLock 在目标目录建锁文件 `.backup.lock`（CreateFile 原子创建，记录 PID）。如果是崩溃残留的锁、且对应进程已退出，会自动清理后重试。另有 RAII 守卫 BackupLockGuard 自动释放。

### Q29：GUI 里保存的任务密码怎么存的？
【背】用 Windows **DPAPI**（CryptProtectData）加密后再十六进制编码存到 tasks.dat，只有当前用户能解密，不明文落盘。

## 四、健壮性与异常处理（老师脚本测试相关）

### Q30：如果备份过程中进程被强杀、或文件千奇百怪，怎么保证不损坏？
【背】几个机制配合：
1. **原子写入**：先写临时文件 `.baktmp`（文件名带 PID 保证唯一），写完再替换正式文件，不会留下半个正式文件。
2. **崩溃残留恢复**：启动时扫描 data/，用 ResidualUtil 识别 `.baktmp`、`.baktmp.old`、加解密临时文件，清理临时文件、恢复旧数据。
3. **备份失败不覆盖旧 Manifest**：备份被取消或有失败时保留上一次完整清单。
4. 专门写了健壮性测试脚本，造特殊字符/中文/emoji/空文件/全 0/全 0xFF/超长路径/深层嵌套/只读隐藏等 135 个文件，三种加密模式全部备份-校验-恢复-逐字节比对通过。

### Q31：文件被其他程序占用、或单个文件读失败怎么办？
【背】打开文件时设置共享读/写/删除，尽量读到被占用文件；单个条目失败会记录错误并继续，不中断整个备份，最后汇总到 BackupResult 的错误列表。

## 五、诚实边界（被问到没做的，别装懂）

### Q32：你这个项目有什么没做 / 不足的地方？
【背】如实说，不编：
1. 没有网络备份、实时备份。
2. 有 2 个测试用例被跳过：TarPacker.SymlinkPreserved 和 FileScanner.SymlinkIsRecordedWithWarning，原因是当前环境没有开发者模式/管理员权限，创建符号链接报 1314 错误——代码逻辑是对的，拿到权限即可通过。
3. 手写 Huffman/RLE 主要用于体现算法原理，压缩率不如成熟的 zstd/deflate；对已经压缩或加密的高熵数据，Huffman 可能不省空间甚至略增。
4. 3DES 已属较老算法，保留它主要是为了体现"多种分组密码 + 不同参数对比"，生产环境首选 AES-256。

### Q33：测试整体情况给个数字。
【背】用 **GoogleTest（gtest）框架**，共 **21 个测试文件、29 个测试套件、133 个测试用例：131 通过、2 跳过**（跳过原因见 Q32）。测试种类覆盖：单元测试、模块集成测试、端到端备份恢复测试、健壮性/压力测试。压缩部分覆盖空数据、单字节、单符号、全相同、随机字节、256 符号、跨块大文件、截断损坏检测和压缩+加密组合。每个模块都有对应测试文件。
